# Deploying a separate testing site — https://flatcare.dineflowpro.com/

This sets up **flatcare.dineflowpro.com** as a fully independent copy of the
app, isolated from production (**flatcare.in**), so you can test changes
without any risk to live data or live payments. Same codebase, same repo —
just a second, separate deployment with its own files, its own `.env`, and
its own database.

Read [DEPLOYMENT.md](DEPLOYMENT.md) first — this file only calls out what's
*different* for the testing site.

## 1. Two separate copies of the code — never share one folder

Do not point both domains at the same project folder on the server. Each
site needs its own directory tree (its own `vendor/`, `storage/`,
`bootstrap/cache/`, and — critically — its own `.env`):

```
/home/<cpanel-user>/flatcare/            (production — flatcare.in)
/home/<cpanel-user>/flatcare-testing/    (testing — flatcare.dineflowpro.com)
```

Clone the repo into the second folder separately (`git clone` a second time,
or `git clone --branch testing` if you want testing to track a different
branch than production). Do **not** symlink or copy one into the other —
that's how a testing deploy silently changes production files.

## 2. cPanel subdomain

Since `dineflowpro.com` is the account's domain and `flatcare` is a
subdomain of it, create it in cPanel under **Domains → Subdomains**:

- Subdomain: `flatcare` on domain `dineflowpro.com`
- Document root: point it at `flatcare-testing/public` (the **Preferred**
  option from DEPLOYMENT.md §2 — a subdomain gets its own document-root
  field in cPanel, so you don't need the `.htaccess` rewrite trick at all).

This keeps testing's web root physically separate from production's, so a
misconfiguration on one can't expose the other's `app/`, `.env`, etc.

## 3. Separate database (with the same `CREATE DATABASE` privilege)

In cPanel → **MySQL Databases**, create a *new* database and user just for
testing, e.g. `<prefix>_flatcare_test` — do not reuse the production
database or user. As with production (DEPLOYMENT.md §3, "Important: the
multi-tenant database privilege"), this app provisions a new physical MySQL
database per society at signup — the testing DB user needs `ALL PRIVILEGES`
(cPanel's "add user to database" grants this, which includes `CREATE`), or
test society signups will fail at the provisioning step. Using a dedicated
test DB user means test signups create their tenant databases separately
from production's, so nothing you do while testing ever touches a real
society's data.

## 4. Testing `.env`

Same fields as DEPLOYMENT.md §3, with these differences:

```env
APP_NAME="FlatCare (Testing)"
APP_ENV=testing
APP_KEY=                      # generate separately — do NOT reuse production's key
APP_DEBUG=true                # fine to leave on here; keep false on production
APP_URL=https://flatcare.dineflowpro.com

DB_DATABASE=<prefix>_flatcare_test
DB_MAIN_DATABASE=<prefix>_flatcare_test
DB_USERNAME=<testing db user>
DB_PASSWORD=<testing db password>

# Keep Razorpay in TEST mode here — never put live keys on the testing site.
RAZORPAY_KEY_ID=<test key id>
RAZORPAY_KEY_SECRET=<test key secret>
```

Everything else (mail, session driver, queue) can mirror production, or stay
on simpler defaults (e.g. `MAIL_MAILER=log`) if you don't need testing to
send real emails.

## 5. Deploy steps (run inside `flatcare-testing/`)

Same as DEPLOYMENT.md §4:

```bash
composer install --no-dev --optimize-autoloader
npm ci && npm run build
cp .env.example .env             # then fill in the testing values above
php artisan key:generate --force
php artisan migrate --force
php artisan storage:link
php artisan config:cache
php artisan route:cache
php artisan view:cache
```

## 6. Keep search engines and users out of the testing site

`/robots.txt` is generated by a route (`routes/web.php`), not a static file,
and automatically returns `Disallow: /` whenever `APP_ENV` isn't
`production` — so as long as testing's `.env` has `APP_ENV=testing` (§4
above), nothing extra is needed here.

Optionally protect the site further with cPanel's **Directory Privacy**
(password-protect the subdomain's document root) since it's a real,
publicly-reachable URL otherwise.

## 7. Mobile app

Leave the Flutter app's `API_BASE_URL` pointed at production
(`https://flatcare.in/api/v1`) unless you're specifically testing the mobile
API — see DEPLOYMENT.md §5. If you do need a test build, use
`--dart-define=API_BASE_URL=https://flatcare.dineflowpro.com/api/v1` for
that build only; don't change the release pipeline's default.

## Day-to-day workflow

- Push/pull changes into `flatcare-testing/` and test there first.
- Once verified, deploy the same commit into `flatcare/` (production) using
  DEPLOYMENT.md.
- The two `.env` files, two databases, and two document roots mean nothing
  you do on `flatcare.dineflowpro.com` can affect `flatcare.in` — that
  isolation is the whole point of keeping them as separate folders instead
  of one shared deployment.
